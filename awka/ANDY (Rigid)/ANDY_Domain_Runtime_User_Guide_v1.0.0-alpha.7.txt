======================================================================
1. PURPOSE OF THIS GUIDE
======================================================================

This guide explains how to install, activate, and operate the ANDY Domain
Runtime v1.0.0-alpha.7.

ANDY means Adopted Narrative Directional Yielder.

ANDY manages long-running, structured, artifact-centered workflows from
narrative intake through:
- workflow creation;
- user-provided narrative adoption;
- narrative validation;
- exact stage prompt submission;
- stage execution;
- draft artifact generation;
- artifact registration;
- artifact acceptance or rejection;
- Evidence Packet attachment;
- artifact dependency-eligibility promotion;
- stage completion evaluation;
- explicit stage completion confirmation;
- stage advancement;
- workflow finalization;
- controlled final artifact-set export;
- Artifact Receipt and Artifact Set Receipt generation;
- artifact body resolution;
- export projection QA;
- runtime state serialization;
- workflow closure.

ANDY runs as a Domain Runtime on AWKA. AWKA must be bootstrapped and READY
before ANDY is activated.

The most important operating rule is:

Accepted dependency-eligible artifacts and Evidence Packets, as represented in
committed Canonical State, form the authoritative procedural record.
Conversation history, model output, draft artifacts, registered-only artifacts,
accepted-pending-evidence artifacts, rejected artifacts, disallowed artifacts,
out-of-band files, and tool output are not active procedural context unless
admitted through registered ANDY Capabilities and Validators.

ANDY is not a general conversation mode. A workflow is not a conversation. A
workflow is a governed narrative composed of procedural stages, artifact slots,
accepted artifact versions, Evidence Packets, Snapshots, receipts, and
explicit user-confirmed transitions.

======================================================================
2. RIGID ALPHA.7 OPERATING NOTE
======================================================================

ANDY v1.0.0-alpha.7 is a rigid governance version of ANDY.

Rigid means that the workflow is intentionally controlled by registered
Capability routes, Validator gates, precondition checks, stage state, artifact
slot requirements, Evidence Packet linkage, and explicit user-confirmed
transitions. The user may request action, but the user cannot bypass the
workflow contract by using vague language, shorthand commands, premature
advancement, or conversational approval.

The first alpha.7 workflow test demonstrated this rigidity:
- an incomplete stage execution command did not mutate state;
- a shorthand Accept command did not accept an artifact;
- an attempt to evaluate and advance in the same command evaluated the stage but
  blocked advancement until explicit completion confirmation occurred;
- every accepted artifact still had to enter the registered artifact lifecycle;
- every stage still had to be evaluated, explicitly confirmed, and advanced;
- finalization, export, and closure remained separate governed operations.

This is expected behavior. ANDY alpha.7 is designed so that not even an
authorized user can deviate from the active governance workflow. Authority is
expressed through exact registered commands, not through conversational intent.

6. AWKA ALPHA.4 EVENT REGISTRY PROJECTION COMPATIBILITY
======================================================================

AWKA v1.0.0-alpha.4 accepts only its fixed candidate Definition Registry set
at activation publication time.

Therefore, ANDY alpha.7 must not publish a first-class event_registry during
AWKA alpha.4 activation.

Instead, ANDY alpha.7 publishes:

schema_registry["ANDY.SCHEMA.EVENT_REGISTRY_CATALOG"]

This catalog preserves canonical ANDY Event Registry semantics while remaining
compatible with AWKA alpha.4. It contains all canonical ANDY event definitions
and supports event contract resolution without extending AWKA alpha.4's fixed
registry set.

Expected activation-publication registry set:
- entity_registry;
- capability_registry;
- validator_registry;
- renderer_registry;
- workflow_registry;
- tool_registry;
- schema_registry;
- policy_registry.

Activation must fail if the candidate publication set includes event_registry
as a first-class registry under AWKA alpha.4.

7. ANDY WORKFLOW STRUCTURE
======================================================================

An ANDY workflow is a linear procedural narrative.

The basic structure is:

Narrative
-> Stage 1
-> Stage 2
-> Stage 3
-> ...
-> Final Stage

Each stage may define:
- a unique stage ID;
- a stage order;
- a stage name;
- an objective;
- required inputs;
- expected outputs;
- required artifact slots;
- optional artifact slots;
- disallowed artifact types;
- evidence requirements;
- completion criteria;
- transition rules.

Alpha.7 supports rigid linear ordered narratives only. It does not support:
- user-directed bypass of registered commands;
- conversational stage advancement;
- implicit artifact acceptance;
- implicit evidence attachment;
- branching;
- parallel stages;
- reusable narrative libraries;
- multi-agent delegation;
- production authentication infrastructure.

A stage does not execute automatically. A user-provided stage prompt must be
submitted before the stage can execute.

======================================================================
8. CORE WORKFLOW LIFECYCLE
======================================================================

The normal alpha.7 lifecycle is:

1. Bootstrap AWKA.
2. Activate ANDY.
3. Run New ANDY Workflow.
4. Adopt ANDY Narrative.
5. Run a stage to review with an explicit prompt payload.
6. Review draft artifact candidates.
7. Accept artifact with evidence, or reject/request revision.
8. Evaluate stage completion.
9. Confirm stage complete.
10. Advance from the stage.
11. Repeat for remaining stages.
12. Finalize workflow.
13. Export artifact set.
14. Validate final export projection integrity.
15. Create Artifact Receipts and Artifact Set Receipt.
16. Close workflow.

Artifact acceptance and stage completion are separate. Accepting required
artifacts does not automatically advance the workflow. The user must explicitly
evaluate completion, confirm completion, and advance the stage.

9. DOMAIN ROLES AND AUTHORITY
======================================================================

ANDY distinguishes human authority, AI proposal, and tool execution.

Common human roles:
- andy_owner;
- andy_operator;
- andy_approver;
- andy_admin.

Approver roles:
- andy_owner;
- andy_approver.

AI and tool identities may generate candidate content or technical provenance,
but they may not approve artifacts, confirm stage completion, populate human
approval fields, or bypass registered workflow transitions.

Typical authority rules:
- workflow creation requires an authorized human role;
- narrative adoption requires an authorized human role;
- stage prompt submission requires an authorized human role;
- artifact acceptance requires an authorized approver role;
- artifact rejection requires an authorized human role;
- stage completion requires explicit authorized human confirmation;
- restore and administrative reopening require owner/admin authority.

Human authority is not absolute runtime authority. Even authorized users must
operate through registered commands and legal state transitions.

Vague instructions do not mutate state. Exact payload-bearing commands or
registered workflow commands are required.

10. ALPHA.7 COMPOSITE CAPABILITIES
======================================================================

Alpha.7 has 27 primitive Capabilities and 3 composite Capabilities.

Composite Capabilities reduce user-facing ceremony while preserving primitive
records, primitive events, Validators, partial-failure visibility, Evidence
Packet sequencing, dependency gates, and auditability.

The three composite Capabilities are:

1. ANDY.CAP.ADOPT_NARRATIVE

User-facing commands:

Adopt ANDY Narrative: <payload>

Adopt ANDY Narrative from uploaded file: <filename>

Primitive sequence:
- ANDY.CAP.LOAD_NARRATIVE
- ANDY.CAP.VALIDATE_NARRATIVE

Commit policy:
- all_or_none;
- two-phase candidate validation;
- failed validation commits no canonical narrative.

2. ANDY.CAP.RUN_STAGE_TO_REVIEW

User-facing commands:

Run stage STG-001 with prompt: <payload>

Submit and execute stage STG-001: <payload>

Primitive sequence:
- ANDY.CAP.SUBMIT_STAGE_PROMPT
- ANDY.CAP.EXECUTE_STAGE
- ANDY.CAP.OPEN_STAGE_REVIEW

Commit policy:
- safe_partial_commit;
- prompt commit is durable if later execution or review opening fails;
- failed primitive step must be recorded.

3. ANDY.CAP.ACCEPT_ARTIFACT_WITH_EVIDENCE

User-facing command:

Accept artifact with evidence for slot SLOT-001 in stage STG-001: artifact_ref=<ref> evidence_source=<source> acceptance=<statement>

Primitive sequence:
- ANDY.CAP.REGISTER_ARTIFACT
- ANDY.CAP.ACCEPT_ARTIFACT
- ANDY.CAP.ATTACH_EVIDENCE_PACKET
- ANDY.CAP.PROMOTE_ARTIFACT_DEPENDENCY_ELIGIBLE

Commit policy:
- safe_partial_commit;
- successful prior steps are preserved;
- dependency_eligible must remain false until all required primitive steps
  succeed.

======================================================================
12. STAGE PROMPTS
======================================================================

Each stage requires a user-provided stage prompt before execution.

Preferred alpha.7 command:

Run stage STG-001 with prompt: <payload>

Example:

Run stage STG-001 with prompt: Research abstract kernels, including conceptual foundations, architecture families, abstraction boundaries, verification concerns, and AI orchestration analogues. Produce an evidence-backed report suitable for final export.

The composite command submits the prompt, executes the stage, and opens review.
Internally, it still records the primitive sequence.

Stage prompts are versioned. Only one prompt version may be active for a stage
at a time. Older prompt versions remain audit-visible but inactive.

Prompt versions should record:
- stage_prompt_version_id;
- stage_id;
- prompt_version_number;
- prompt_digest;
- prompt_status;
- active_for_generation flag;
- adapter route evidence.

Stage execution is blocked if no active prompt version exists.

======================================================================
13. INTERACTION ADAPTER GOVERNANCE
======================================================================

The interaction adapter routes user messages to registered ANDY Capabilities.
It is not an independent authority and may not mutate state directly.

When ANDY is active, the adapter must preflight the current state before it
routes a mutating command.

Vague messages do not mutate state. Examples:
- Looks good.
- Approved.
- Continue.
- Next.
- Use that.
- Accept.
- Reject that.
- Fix it.

These messages may trigger clarification or presentation, but they must not:
- commit a prompt;
- accept an artifact;
- reject an artifact;
- attach evidence;
- promote dependency eligibility;
- confirm stage completion;
- advance a stage;
- finalize or close a workflow.

Macro commands mutate only when explicitly payload-bearing and targeted at the
correct current stage. If a user issues a command out of sequence, ANDY must
block the command and return the next registered workflow command.

======================================================================
14. ARTIFACTS AND ARTIFACT SLOTS
======================================================================

Artifacts are the primary mechanism for workflow progression.

Examples include:
- requirements documents;
- specifications;
- architecture documents;
- diagrams;
- research summaries;
- implementation plans;
- generated documents;
- verification reports;
- decision records;
- final deliverable sets.

A stage may declare required and optional artifact slots. A stage is complete
only when required artifact slots are satisfied by accepted_dependency_eligible
artifact versions and the user explicitly confirms the stage complete.

Artifact version statuses include:
- draft;
- registered;
- revision_requested;
- accepted_pending_evidence;
- accepted_dependency_eligible;
- rejected;
- disallowed;
- superseded;
- inactive;
- archived;
- restored_as_new_version;
- nongoverned_out_of_band.

Important distinction:
- accepted_pending_evidence is accepted but not dependency-eligible;
- accepted_dependency_eligible is accepted, evidence-linked, promoted, and may
  satisfy required slots or active context dependencies.

======================================================================
15. DRAFT, ACCEPTED, REJECTED, AND DISALLOWED ARTIFACTS
======================================================================

Draft artifacts are review candidates. They are not active procedural context
and cannot satisfy dependencies.

Registered artifacts are known to ANDY but are not automatically accepted.

Accepted-pending-evidence artifacts have human acceptance but are not yet
dependency-eligible.

Accepted-dependency-eligible artifacts have completed acceptance, Evidence
Packet attachment, and dependency promotion.

Rejected artifacts remain preserved for audit and retrieval. They cannot
satisfy dependencies and cannot participate in active narrative context.

Disallowed artifacts are blocked at generation when detectable and always
blocked at acceptance. Attempts to generate or accept disallowed artifacts must
fail closed.

Out-of-band files are files created outside the registered ANDY artifact flow.
They are not active procedural context and are not dependency-eligible. If a
user explicitly requests a non-governed file while ANDY is active, the response
must state that the file is non-governed unless it is registered through ANDY's
artifact flow.

======================================================================
16. EVIDENCE PACKETS
======================================================================

An Evidence Packet preserves the provenance and validation history of an
accepted artifact.

An Evidence Packet may include:
- evidence_packet_id;
- accepted_artifact_id;
- artifact_version_id;
- validation_status;
- dependency_eligibility_result;
- source_inputs;
- approval_statement;
- artifact_ref;
- artifact_digest.

Accepted artifacts should not be used downstream without Evidence Packet
linkage and dependency-eligibility promotion.

Operator rule for alpha.7:
- do not use placeholder evidence values;
- do not use <source list> as evidence_source;
- do not use <acceptance statement> as acceptance;
- evidence_source should identify concrete sources, source anchors, file names,
  digest references, or other auditable provenance;
- acceptance should be a meaningful human approval statement.

The first alpha.7 workflow demonstrated lifecycle mechanics, but evidence
placeholders should be treated as unacceptable operating practice for serious
runs. Future hardening should reject placeholder evidence values automatically.

======================================================================
17. ARTIFACT ACCEPTANCE WITH EVIDENCE
======================================================================

Preferred alpha.7 command:

Accept artifact with evidence for slot SLOT-001 in stage STG-001: artifact_ref=<ref> evidence_source=<source> acceptance=<statement>

Example:

Accept artifact with evidence for slot SLOT-001 in stage STG-001: artifact_ref=ANDY_Draft_Report.pdf evidence_source=web sources S1-S7 cited in the report and rendered artifact SHA-256 <digest> acceptance=I accept this report as the research artifact for SLOT-001.

Rules:
- acceptance requires an authorized approver;
- evidence_source must not be blank;
- evidence_source should not be a placeholder;
- acceptance must not be blank;
- acceptance should not be a placeholder;
- artifact_ref must identify the artifact candidate;
- dependency_eligible must remain false until registration, acceptance,
  Evidence Packet attachment, and promotion all succeed;
- rejected or disallowed artifacts cannot be promoted.

======================================================================
18. STAGE COMPLETION AND ADVANCEMENT
======================================================================

A stage can complete only when:
- a valid active stage prompt version exists;
- all required artifact slots are satisfied by accepted_dependency_eligible
  artifact versions;
- optional artifacts are accepted, rejected, or explicitly deferred;
- disallowed artifacts are blocked or rejected;
- each accepted artifact has an Evidence Packet;
- rejection history is preserved for rejected artifacts;
- inactive artifacts are excluded from active context;
- an authorized user explicitly confirms stage completion.

Evaluate stage completion:

Evaluate stage completion for STG-001

Confirm stage completion:

Confirm stage complete for STG-001

Advance from the stage:

Advance stage STG-001

Alpha.7 invariant:

stage_status = stage_advanced implies review_status = closed

Stage completion and advancement are separate operations. ANDY must not infer
stage completion from artifact acceptance alone.

23. RUNTIME STATE SERIALIZATION
======================================================================

Alpha.7 requires runtime state serialization consistency.

Final serialized runtime state must satisfy:
- snapshot.active_version == canonical_state.active_version;
- snapshot.current_state == canonical_state.current_state;
- CLOSED workflow has no next registered workflow command;
- stage_status = stage_advanced implies review_status = closed;
- finalized or exported workflow has a finalization record;
- closed workflow has a closure record;
- exported or closed workflow has Artifact Receipts and an Artifact Set Receipt;
- artifact body resolution records exist for exported artifact members;
- export projection QA result exists and is PASS for successful exports.

25. RESTORE AND REOPEN
======================================================================

ANDY uses restore-as-new-version behavior.

Restore a historical Snapshot as a new successor version:

Restore snapshot SNAP-001 as new version

Reopen a prior stage as a new version:

Reopen stage STG-001 as new version

Restoration never overwrites history. The historical Snapshot remains
unchanged, and ANDY creates a new active version derived from it.

======================================================================
26. CLOSE THE WORKFLOW
======================================================================

After the final artifact set is exported and all workflow requirements are
complete, close the workflow:

Close workflow

Closure requires:
- workflow finalization;
- accepted artifact set readiness;
- export eligibility if export is required;
- valid Artifact Receipt and Artifact Set Receipt for final controlled exports;
- no unresolved blocking dependencies;
- authorized closer.

If closure requirements are incomplete, the workflow remains open.

30. COMMON ERRORS AND CORRECTIONS
======================================================================

ERROR: ANDY activation fails because component hashes are pending.
CORRECTION: Replace the preliminary Manifest with the finalized Manifest that
contains exact lowercase SHA-256 hashes and digest_status = verified.

ERROR: ANDY activation fails because event_registry is published as a first-class registry.
CORRECTION: Use the patched alpha.7 reissue. Under AWKA alpha.4, Event Registry
definitions must be published through ANDY.SCHEMA.EVENT_REGISTRY_CATALOG inside
schema_registry.

ERROR: User provides a stage prompt informally, but no prompt version is
created.
CORRECTION: Use the exact payload-bearing command:
Run stage STG-001 with prompt: <payload>

ERROR: A vague message is entered while ANDY is waiting for an exact command.
CORRECTION: Use the registered command with explicit payload. Vague messages do
not mutate.

ERROR: User enters Accept and expects artifact acceptance.
CORRECTION: Use the registered acceptance command with slot, stage,
artifact_ref, evidence_source, and acceptance fields.

ERROR: User tries to advance immediately after evaluation.
CORRECTION: Confirm stage completion first. Run:
Confirm stage complete for STG-001
Advance stage STG-001

ERROR: A draft artifact is used as downstream context.
CORRECTION: Register, accept, attach Evidence Packet, and promote the artifact
to accepted_dependency_eligible.

ERROR: An artifact is accepted but still not dependency-eligible.
CORRECTION: Attach valid evidence and run the dependency-eligibility promotion
through the registered acceptance-with-evidence flow.

ERROR: Evidence uses placeholders such as <source list> or <acceptance statement>.
CORRECTION: Replace placeholders with concrete source references and a real
acceptance statement before treating the run as serious evidence-backed work.

ERROR: A rejected artifact reappears as if it were usable.
CORRECTION: Review rejection history. Rejected artifacts cannot satisfy
dependencies.

ERROR: Final export exists but no Artifact Receipt or Artifact Set Receipt is available.
CORRECTION: Regenerate through ANDY.CAP.EXPORT_ARTIFACT_SET, hash the final
artifact set, validate final projection QA, and create post-hash receipts.

ERROR: selected_snapshot_digest is ambiguous in an export receipt.
CORRECTION: Distinguish canonical snapshot digest from projection or receipt
digest. Treat ambiguous digest lineage as an inspection concern until fields are
clarified.

31. FAIL-CLOSED EXPECTATIONS
======================================================================

ANDY fails closed. When a required check fails, it must not:
- guess missing workflow facts;
- silently repair artifacts;
- treat conversation history as Canonical State;
- treat AI output as accepted artifact content;
- treat tool output as authoritative;
- use draft artifacts as dependencies;
- use registered-only artifacts as dependencies;
- use accepted_pending_evidence artifacts as dependencies;
- use rejected artifacts as dependencies;
- use disallowed artifacts as dependencies;
- create governed artifacts outside registered artifact flow;
- accept vague approval commands;
- accept shorthand commands as mutating commands;
- infer stage completion;
- infer stage advancement;
- bypass registered Capabilities;
- bypass Validators;
- let Renderers mutate Canonical State;
- publish partial Definition Registries;
- publish event_registry as a first-class AWKA alpha.4 registry;
- commit a failed mutation except where a declared safe partial commit policy
  preserves prior successful primitive steps;
- claim a successful final export without final projection QA;
- claim a successful final export without receipts;
- create a Workflow Instance during Domain activation;
- create a Workflow Instance after failed Domain activation.

The system reports the component, failed check, defect, and required correction.
